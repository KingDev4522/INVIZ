PRD 8 — Security Remediation & Snowflake Analytics

Project: INVIZ (ContextLens + VoiceLens)
Document: PRD 8 — Security Remediation & Snowflake Analytics
Version: 1.0 | Date: 2026-10-08 | Status: Proposed — awaiting owner approval
Purpose: (a) Register every defect found in a full line-by-line audit of the shipped
v0.0.2 codebase, severity-ranked with evidence and acceptance criteria; (b) define how
Snowflake is integrated into INVIZ without violating the project's local-first,
zero-provider-key privacy architecture.
Relationship: PRD 1 defines requirements. PRD 2 defines behavior. PRD 3 defines
architecture. PRD 4 defines technical contracts. PRD 5 defines security/privacy policy.
PRD 6 defines the build. PRD 7 is the build confirmation record. This document defines
what must be FIXED, and what gets ADDED on top.

> Scope boundary: This document does NOT redefine product behavior, and does NOT relax
> any PRD 5 privacy invariant. It treats PRD 5 as binding and designs the Snowflake
> integration to satisfy it. It does not add product features; the only functional
> additions are (1) telemetry egress, which is off by default, and (2) the analytics that
> makes the existing LIVE-PENDING SLOs measurable. Every remediation item is a defect
> fix against existing stated intent — the code contradicts its own doc comments or its
> own tests in most cases.

> Reading guide: §0 states the locked constraints. §1 is method + baseline. §2 is the
> findings register — the core deliverable. §3–§5 are remediation specs with acceptance
> criteria. §6 is the test-coverage mandate. §7 is architectural debt. §8–§13 are the
> Snowflake integration. §14 is the delivery plan. §15–§16 are non-goals and open
> questions for the owner.

> Critical reading note: the test suite is 988 tests / 86 files, all green, typecheck
> clean — and the four CRITICAL findings in §3 are all live in production paths that
> have NO test. This document's central engineering claim is that INVIZ's defect rate is
> governed by test SHAPE, not test COUNT. §6 is therefore not optional cleanup; it is
> the primary control.

### C1 — Any website the user visits can drive the AI gateway
**Severity: CRITICAL** · **Status: LIVE** · **Exploit: remote, no user action beyond
visiting a page**

`backend/src/http.ts:11-32`

    res.setHeader("Access-Control-Allow-Origin",
      typeof origin === "string" && origin !== "" ? origin : "*");
    res.setHeader("Vary", "Origin");
    res.setHeader("Access-Control-Allow-Methods", "GET, POST, OPTIONS");
    const requested = req.headers["access-control-request-headers"];
    res.setHeader("Access-Control-Allow-Headers",
      typeof requested === "string" && requested !== "" ? requested
        : "Content-Type, Authorization");
    res.setHeader("Access-Control-Allow-Private-Network", "true");
    res.setHeader("Access-Control-Max-Age", "86400");

`backend/src/http.ts:70-72`

    export function checkAuth(req, configuredToken) {
      if (configuredToken === "") return true;

And the shipped default is empty — `backend/.env.example:76`:

    # Leave empty ONLY for loopback development.
    BACKEND_TOKEN=

The boot log confirms the open mode is live — `configSummary` reports
`"authMode":"open-loopback-dev"`.

Impact:
  - Any origin is reflected; requested headers are echoed back; private-network access
    is unconditionally granted. Any page can `fetch("http://127.0.0.1:8787/v1/tts",
    {method:"POST", ...})` and READ the response.
  - Loopback binding is not a mitigation — the browser runs on the victim's own machine.
  - `/v1/validation` performs LIVE PAID provider calls on every request
    (`backend/src/routes/health.ts:139-148` runs `checkGroq` + `checkTts` +
    `checkOpenRouter`). An attacker page can loop it at zero cost to themselves.
  - `/v1/search` spends one Tavily credit per call.
  - `setCors` has ZERO test coverage (`backend/src/http.test.ts` has no CORS case).

C2 below compounds this: because the system prompt is client-controlled, C1 gives any
website both the gateway AND control of the safety instructions given to the model that
drives the user's browser.

### C2 — Client can replace the backend's entire safety system prompt
**Severity: CRITICAL** · **Status: LIVE** · **Reachable remotely via C1**

`backend/src/routes/chat.ts:201`

    systemPrompt: typeof body["systemPrompt"] === "string"
      ? body["systemPrompt"] : undefined,

`backend/src/ai/qwen-client.ts:404`

    { role: "system", content: input.systemPrompt ?? SYSTEM_PROMPT_V1 },

`SYSTEM_PROMPT_V1` (`backend/src/ai/schemas.ts:12-39`) carries every guardrail in the
product: "NEVER emit JavaScript, selectors, URLs", the `chrome://`/`file:` refusal rule,
the never-request-a-password/OTP rule, the closed action-key list, and the JSON-only
output contract. All of it is client-overridable, unbounded in length (only the 8 MB body
cap applies), on the ONE route that produces browser actions.

`enrichPage` and `qa` are unaffected — they hardcode their prompts.

### C3 — Voice-driven open-redirect: "open <any-domain>" is navigated to with no
       confirmation
**Severity: CRITICAL** · **Status: LIVE** · **Code contradicts its own comment**

`frontend/src/background/agent-controller/controller.ts:395-413`

    // directly - no reasoning call, no search, no skill selection. Anything not
    // listed in OPEN_SITE_ALLOWLIST still goes through the model.        <-- FALSE
    const OPEN_SITE_RE =
      /^(?:please\s+)?(?:open|go to|goto|launch|visit)\s+(?:www\.)?
        (youtube|github|twitter|x|google|reddit|wikipedia|[a-z0-9-]+\.[a-z]{2,})
        (?:\.com)?\s*(?:please)?[?.!\s]*$/i;

    export function resolveOpenSiteDestination(goal: string): string | null {
      ...
      if (/^[a-z0-9-]+\.[a-z]{2,}$/i.test(key)) {
        return `https://${key}/`;                     // <-- escapes the allowlist
      }
      return null;

`OPEN_SITE_ALLOWLIST` (`shared/constants.ts:129-137`) is exactly 7 frozen entries. The
regex fallback lets ANY domain bypass it entirely. The same hole exists in the compound
path at `controller.ts:436`.

Consequences:
  - "open paypal-secure-login.com" → deterministic `navigate`, `confirmed: false`.
  - WebGuard treats `navigate` as a targetless action (`webguard/policy.ts:80`), so
    `REQUIRE_CONFIRMATION` is never emitted.
  - Any speech-recognition confusion becomes an unconfirmed navigation to an
    attacker-chosen host.
  - For a BLIND user — who cannot see the address bar change — this is a textbook
    voice-phishing vector. It is the highest-harm finding in this document relative to
    the target user population.

### C4 — Click verification is vacuous; the agent believes every click succeeded
**Severity: CRITICAL** · **Status: LIVE** · **Defeats the entire verify loop**

`frontend/src/background/agent-controller/controller.ts:2145-2147`

    const defaultExpect: Expectation = sideEffecting
      ? { type: "submit_completed", ...(target !== null ? { target: target.id } : {}) }
      : { type: "element_present" };

`frontend/src/verification/verification-engine.ts:71-72`

    case "element_present":
      if (facts.targetPresent === true) return decided("VERIFIED_SUCCESS");

`identity` is set for any target found in the snapshot (`controller.ts:2169`), so
`targetPresent` is TRUE on the very first 250 ms poll — the clicked element is still on
the page. Therefore every `click`, `focus`, `scroll`, and `press_key` returns
`VERIFIED_SUCCESS` without observing any effect whatsoever.

`stateChanging` (`:2148`) only extends the timeout; it never upgrades the expectation to
`element_state`.

Consequences: `task.completedActions += 1` (`:2176`), the recovery budget resets
(`:2178`), and a dead button is reported as done. PRD 6 §2's "act → verify" loop is
formally present but semantically inert for the most common action type.

§8. SNOWFLAKE INTEGRATION — FIT, CONSTRAINTS, NON-GOALS
================================================================================

## 8.1 The honest tension

INVIZ is a local-first, zero-provider-key, privacy-audited accessibility tool for blind
users. K1–K9 (§0) are binding. Therefore:

> **Snowflake must never sit in the request path of a voice turn, and must never
> receive un-redacted page content, screenshots, or user speech.**

Any design that adds latency to a turn, or that ships page text to a cloud, destroys the
product. This is not a stylistic preference — it is the product.

## 8.2 The fit is unusually good, because the hooks were already built

Three subsystems were **designed for exactly this and never wired**:

| Asset | Location | Verification | Why it fits |
|---|---|---|---|
| `trackEvent()` + 9-event metadata-only allowlist, default-off | `shared/logger.ts:56-84` | **Confirmed zero call sites outside `shared/logger.ts`** | A ready-made metadata-only event API that was never finished |
| `EpisodeStore` port: `load()` / `save(serialized)` / `clear()` | `frontend/src/learning/episode-store.ts:30-34` | Confirmed, with `MemoryEpisodeStore` as the test impl | A clean hexagonal seam. An `Episode` is already a redacted, versioned, JSON per-task event log with a natural PK, natural time columns, and natural dimensions |
| `mcp/mcp-server.ts` + `mcp-protocol.ts` | `frontend/src/mcp/` | **Confirmed zero call sites** | 7 validated tools; Snowflake ships a managed MCP server speaking the same protocol |

Plus two facts that make ingestion cheap:
  - The backend already emits **single-line JSON** to stdout at a single choke point
    (`shared/logger.ts:37`) with `redactObject` applied to every payload (`:36`), and a
    **stable field vocabulary**.
  - The backend emits an unusually rich, already-structured latency record per turn
    (`backend/src/routes/chat.ts:100-139`: `t2_captureMs`, `t4_encodeMs`, `t5_contextMs`,
    `t7_to_t8_inferenceMs`, `t8_to_t9_validateMs`, `backendTotalMs`, image dims/bytes).

## 8.3 Non-goals (explicit)

| Non-goal | Reason |
|---|---|
| Snowflake in the reasoning path | Violates the ≤4 s command→ack SLO (`docs/slo-report.md:25-33`). Warehouse round-trip is 100 ms–seconds. |
| Storing raw page content, screenshots, transcripts, or spoken goals | K2/K3. Category C values must never reach telemetry. |
| Snowflake credentials in `frontend/` | K1. |
| A Node Snowflake SDK in `backend/` | K7 — zero runtime dependencies is a load-bearing property. |
| Snowflake deciding whether an action is safe | K8. WebGuard is the sole authorization gate. |
| A warehouse-validated skill executing without on-device validation | K9. |
| Telemetry ON by default | PRD 5 opt-in discipline. |

## 8.4 The architecture

    |  recorder.finalize(episode)                           |
    +---------------------------+----------------------------+

                                v

§9. TIER 1 — TELEMETRY & ANALYTICS PIPELINE
================================================================================

## 9.1 Scope

Turn the 7 `LIVE-PENDING` SLOs in `docs/slo-report.md:25-33` from "pending" into
measured, and give the product a fleet-level view of failure modes. That is the whole
of Tier 1. Nothing else.

The 7 pending SLOs, all of which are ALREADY LOGGED FIELDS:
  1. Focus → first audio ≤800 ms p95 (warm + cold reported separately)
  2. Capture stop → transcript ≤2.5 s (≤15 s audio)
  3. Voice command → spoken ack/question ≤4 s
  4. Action → verification verdict ≤5 s (local DOM)
  5. Demo A + B pass 5/5 ×2, EN + HI
  6. Bilingual audible matrix (qualitative)
  7. Mic loopback: zero self-transcription

## 9.2 Data flow

  - `trackEvent` is called from the FIVE decision points that already exist in the
    controller: WebGuard `BLOCK` (`:2082`), `confirmation_requested` (`:2101`),
    `action_executed` (`:2181`), `verification_failed` (`:2217`), `task_cancelled`
    (`:2552`). Plus `extension_started` and `voicelens_enabled`.
  - Payloads are metadata only: `taskId`, `pageGeneration`, `actionType`, `targetId`,
    `verificationStatus`, `errorCode`, `latencyMs`, plus a `pageHost` derived field.
  - The extension POSTs batches to a new `PUT /v1/telemetry/flush` route.
  - The backend enqueues and flushes asynchronously.

## 9.3 Non-blocking guarantee (the hard requirement)

> A telemetry failure must be indistinguishable, from the user's perspective, from
> telemetry not existing.

Concrete obligations:
  - Enqueue is **synchronous and O(1)** and NEVER throws.
  - The flush is NEVER awaited inside `stepOnce`, `doAction`, or any speech path.
  - The queue is **bounded** (`MAX_QUEUE = 500`, drop-oldest) so memory cannot grow.
  - On flush failure: drop the batch, increment a counter, log at `debug` only. Never
    retry in a way that can grow the queue. Never surface to the user (K6 — no new
    error codes, no new speech strings).
  - A `TELEMETRY_DISABLED` state must cost nothing measurable. Budget: enqueue <50 µs.

## 9.4 Backend implementation sketch

    // backend/src/telemetry/outbox.ts   (new)
    type TelemetryEvent = {
      event: string; ts: number; taskId?: string; pageGeneration?: number;
      actionType?: string; targetId?: string; verificationStatus?: string;
      errorCode?: string; latencyMs?: number; pageHost?: string;
    };

    const MAX_QUEUE = 500;
    const queue: TelemetryEvent[] = [];
    let dropped = 0;

    export function record(e: TelemetryEvent): void {   // sync, O(1), NEVER throws
      if (!telemetryEnabled) return;
      try {
        queue.push(redactObject(e) as TelemetryEvent);   // K3: single redaction point
        if (queue.length >= MAX_QUEUE) { queue.shift(); dropped += 1; }
      } catch { /* telemetry must never throw */ }
    }

    export function drain(): TelemetryEvent[] { const b = queue.slice(); queue.length = 0; return b; }

The uploader calls `drain()` and writes NDJSON. Per K7, use a thin `fetch` against the
Snowflake SQL REST API (`POST /api/v2/statements` with a `MULTI_STATEMENT_COUNT`
batch), or run the uploader as a **separate out-of-process script** so `backend/`
gains zero dependencies. Recommended: separate process. It also means a hung warehouse
connection can never affect the gateway.

================================================================================
§11. TIER 2 — FLEET LEARNING LOOP
================================================================================

## 11.1 The gap this closes

Today `proposeCandidateFromEpisode` (`learning/candidate.ts:107-209`) mines **exactly one
episode at a time** and runs only in tests. It structurally cannot notice that 40
episodes across 12 users each did the same 3 actions on the same host. That is the single
biggest latent capability in the codebase — and it is currently unreachable.

## 11.2 Cross-episode candidate mining

    SELECT PAGE_HOST, GOAL_HASH,
           MODE() WITHIN GROUP (ORDER BY ACTION_TYPE) AS action_seq,
           COUNT(*)                        AS episodes,
           AVG(COMPLETED_ACTIONS)         AS avg_len,
           SUM(IFF(SUCCESS,1,0))/COUNT(*) AS success_rate
    FROM   FACT_EPISODE_ACTION JOIN FACT_EPISODE USING (EPISODE_ID)
    GROUP  BY 1, 2
    HAVING COUNT(*) >= 20 AND success_rate > 0.8
    ORDER  BY episodes DESC;

Emits **ranked** `SkillCandidate` proposals, pushed to devices as suggestions.

## 11.3 Cortex Search over failure text (targets an admitted product limit)

`docs/ARCHITECTURE.md:307-313` admits: small local models cannot reliably hold the JSON
action contract across multi-step tasks, so agency quality still depends on the cloud
tier. A retrieval layer that tells the model "this class of goal has historically failed
here, and here is what worked" attacks that limit directly.

Index:
  - **failure text** — `finalOutcomeText` + `expectType` for failed actions
  - **successful action sequences** — as few-shot exemplars

Feed into `/v1/enrich` as **advisory context only**. Per K8 and the Layer-B rule in
`ARCHITECTURE.md:48`, enrichment is `MODEL_INFERENCE` provenance and is **never
authorization**. It cannot loosen a WebGuard verdict.

**Embedding model constraint (K5):** must be multilingual. `snowflake-arctic-embed-m-v1.5`
is **English-only and PROHIBITED**. Use `voyage-multilingual-2` or
`snowflake-arctic-embed-l-v2.0-8k`.

## 11.4 The device disposes (K9 — non-negotiable)

A warehouse proposes; the device disposes. Any proposal arriving from Snowflake MUST
still pass, on-device, before it can become a skill:
  1. `validateSkill` (`shared/types.ts` / `skill-validation.ts`)
  2. `validateStructuredAction` — closed schema, `KNOWN_FIELDS`, `ELEMENT_ID_RE`,
     `PRESS_KEY_ALLOWLIST`, `NAVIGATE_DENIED_SCHEMES`
  3. `ALLOWED_STEP_FIELDS` (`candidate.ts:216-225`) — rejects smuggled fields
  4. The CDP / shell / `eval` structural rejection in `candidate.ts`
  5. `status: "candidate"`, `testStatus: "untested"`, `canaryRolloutPercent: 0` — a
     remote proposal NEVER arrives pre-trusted

If any step rejects it, it is dropped and the rejection is logged locally. A warehouse
must not be able to shortcut local validation. Add an explicit test asserting a
hostile warehouse response cannot produce a `trusted` skill.

§12. TIER 3 — MCP (OPTIONAL, GATED, LAST)
================================================================================

Snowflake shipped a managed MCP server (GA 2026-08-07) exposing `CORTEX_SEARCH_SERVICE_QUERY`,
`CORTEX_ANALYST_MESSAGE`, `CORTEX_AGENT_RUN`, `SYSTEM_EXECUTE_SQL`, over OAuth 2.0, MCP
revision `2025-11-25`. INVIZ already has an unwired MCP server with 7 validated tools.
The fit is aesthetically perfect and operationally a trap. Reasons to defer:

  1. `SYSTEM_EXECUTE_SQL` exposed to an agent that operates a BLIND USER'S BROWSER is a
     genuine hazard. At most, a read-only Cortex Search tool may ever be exposed.
  2. `frontend/src/mcp/mcp-server.ts` is **dead code with 428 lines of tests** and has
     never executed in production. `shared/mcp-protocol.ts` also cannot negotiate MCP
     rev `2025-11-25`.
  3. There is no `externally_connectable` and no MCP permission in the manifest.
  4. It adds a network dependency to a product whose reliability claim is
     "backend down ⇒ honest 'AI service unavailable'", never a hang.

**Recommendation: do not build Tier 3 in this program.** If it is later wanted, build it
FRESH as a narrow read-only "learned site knowledge" tool, route it through `wiring.ts`
so WebGuard sees it, keep `SYSTEM_EXECUTE_SQL` permanently disabled, and require a
separate owner decision (§16). Tier 1 + Tier 2 deliver the entire value without it.

Note: `handleMcpRequest` and `AgentController.submitAction` should be deleted or gated
per §5.3 regardless of whether Tier 3 ever happens. Shipping 1000 lines of unwired code
with 428 lines of tests is an active liability.

§13. PRIVACY & DATA-PROTECTION GATES
================================================================================

Non-negotiable. Each gate is a release blocker.

## 13.1 Default-off and informed consent

  - `setTelemetryEnabled(false)` ships as the default. No env var flips it on; only an
    explicit user action in the Options page.
  - The Options UI does not exist yet — build it as part of Tier 1, stating plainly what
    is sent, and providing a WORKING DELETE.
  - The toggle must survive `wiring.ts:28-36`-style fail-closed reads.
  - No dark patterns: the toggle defaults off, and is not pre-checked.

## 13.2 Column masking in Snowflake

  - `GOAL_HASH`, `PAGE_TITLE_HASH`, `PAGE_HOST`, `TARGET_ID` carry masking policies so
    even account analysts cannot reverse them.
  - Raw free text (`finalOutcomeText`, `goal`) is NEVER ingested in the first place.
    Hash at the source.

## 13.3 Retention, Time Travel, and erasure

  - `deleteEpisode` / `clearEpisodes` (`episode-store.ts:201-216`) already imply GDPR-style
    erasure. **If the warehouse copy cannot be erased, that is a compliance bug**, because
    the user believes they deleted.
  - Set `DATA_RETENTION_TIME_IN_DAYS` on raw tables; map the Options delete button to a
    real `DELETE`; document Time Travel's own retention as part of the erasure story.
  - Define and publish the retention window in the Options UI.

## 13.4 Fix the leak that already exists FIRST (R-M35)

`content/content.ts:462` logs full `location.href` with query strings on **every page
load, on every site**, and `shared/redact.ts` has **no URL or query scrubbing at all**.

> Do NOT build an egress path on top of an unbounded URL log. R-M35 is a PREREQUISITE
> for Tier 1, not a co-requisite. Ship it first.

## 13.5 Enforce the screenshot bound (R-M36)

`MAX_HYBRID_IMAGE_B64_CHARS` exists in `shared/constants.ts:88` and is referenced
NOWHERE. **Pixels never leave the machine, ever.** Enforce the bound client-side in
`controller.ts` and add a test. The `LOCAL-ONLY` rule in `ARCHITECTURE.md:377-380` is
load-bearing for the privacy model and currently has no enforcement point in the client.

## 13.6 The three highest-risk fields

`pageUrl`, `pageTitle`, `finalOutcomeText`. `safePageUrl` (`episode.ts:128-138`) strips
query and fragment but **retains host + path**, and paths are frequently identifying
(e.g. `/users/<name>/...`). Hash host, hash title, and DROP `finalOutcomeText` from the
Tier 1 payload entirely — keep it locally for diagnostics, where it stays on-device.

## 13.7 Governance features to use

Snowflake's Horizon Catalog / Iceberg interoperability (GA 2026) allows a masking policy
to travel with the table. Use it so the protection is a property of the DATA, not of a
dashboard someone forgets to configure.
